# 五、接口先行、Mock 并行与 Feature Review

以下为本实验建议的**协作流程与评审模板**；没有提供真实参与人员或 GitHub PR 记录，因此不冒充已经发生的团队协作。

## 1. 接口先行

以 `docs/03-接口文档.md` 与 `model/Product.ets` 固定商品结构、错误语义及导航参数。任何成员开始写页面前都应先确认 `ProductGateway.list()` 返回 `Promise<Product[]>`、空数组是正常结果、抛异常是失败。

## 2. 并行任务与可合并边界

| 建议 Feature | 工作项 | 验收方式 |
| --- | --- | --- |
| `feature/http-gateway` | HttpClient、真实 Gateway、响应校验 | 断网、非 2xx 与字段错误验证 |
| `feature/mock-gateway` | MockGateway、成功/空/失败数据 | 3 种模式与延时可复现 |
| `feature/catalog-state` | CatalogStore、快照、并发保护、Preferences | 连点切源和重启恢复 |
| `feature/product-ui` | 页面、列表、状态面板、详情路由 | 商品跳转、保存返回与 Tab 切换 |
| `feature/docs-delivery` | 需求、接口、原型、README、测试与答辩 | 文档交叉引用完整 |

建议每个 Feature 从 `main` 创建独立分支。契约若发生调整，应先更新 `docs/03-接口文档.md` 再修改两种 Gateway。Mock 使 UI 不必等待真实 API 可用，可并行完成页面层。

## 3. Feature Review 提交清单

- [ ] 变更对应需求编号、文件路径和可见行为
- [ ] 没有把网络请求写进页面层、没有在组件里读写 KV
- [ ] 成功、空数据、失败、重试都有对应逻辑
- [ ] 路由参数检查、请求竞态和收藏写盘异常已处理
- [ ] 数据源为真实接口还是 Mock 已如实标注
- [ ] 本机完成编译与模拟器验证，并提供实际截图/日志
- [ ] README、契约、测试记录与代码一致

## 4. 评论规范：先肯定，再给执行建议

**对 HTTP Feature 的建议**：接口数据转换与页面解耦做得清楚，Mock 与真实实现共享数据契约。建议再补充字段类型不符合约定时的错误路径，并断网测试，确保错误码不会被统一改成“暂无商品”。

**对 UI Feature 的建议**：成功、空态和错误状态的切换清晰，商品卡片也得到复用。建议快速连续点击三种模式，观察最后一次请求是否胜出；若旧数据覆盖新界面，在 Store 中检查 `generation`。

**收到反馈后的处理**：先记录复现步骤，再说明对应改动和测试结果；若未完成验证，应标记“待复测”，而不是直接声称已解决。
